# Dating App — reverse-engineering pet-project

Учебный full-stack проект: вертикальная лента знакомств (как TikTok) с матчингом,
дабл-тап лайками и виртуальными/реальными подарками. Реверс-инжиниринг реального
приложения с упором на грамотную архитектуру и лучшие практики.

## Режим работы (важно)

Это **учебный** проект. Цель — не только рабочий результат, но и моё понимание кода.

- Объясняй решения, а не выдавай готовый код молча. В незнакомых мне областях
  (NestJS, тестирование) идём **по частям** — я должен понимать каждый кусок,
  а не получать сразу целый модуль.
- Где есть выбор — предлагай варианты с trade-off, а не решай за меня молча.
- **НЕ пиши тесты за меня.** Тесты я пишу сам как практику (Jest, React Testing
  Library). Твоя роль — подсказывать что покрыть, ревьюить мои тесты, объяснять
  ошибки. (см. раздел «Тестирование»)

## Оценка необходимости тестов

При планировании **каждого** экрана/фичи оцени, насколько здесь нужны тесты, по 3
градациям, и подсвети это в плане ДО реализации:

- **Очень важны** — сложная логика, легко сломать, высокая цена ошибки
  (логика матчинга, авторизация, расчёты, пагинация).
- **Умеренно важны** — логика есть, но простая; тесты полезны, но не критичны
  (форма с валидацией, условный рендер).
- **Минимально важны** — тонкий UI без логики, тестировать почти нечего
  (статичный экран, чистая вёрстка).

Это нужно, чтобы я осознанно решал, куда вкладывать время на тесты, а где не тратить.

## Стек

- **Frontend:** Vite + React + TypeScript, React Router, Apollo Client,
  shadcn/ui + Tailwind, ESLint (flat config, eslint.config.js).
- **Backend:** сейчас — мок-сервер на Apollo Server + `@graphql-tools/mock`
  (schema-first). Позже — NestJS + Prisma + PostgreSQL.
- **Структура:** один репозиторий, папки `backend/` и `frontend/`. Без
  монорепо-тулинга (Nx/Turborepo не нужны: два независимых приложения, граф
  зависимостей плоский, шаринг типов закрыт через codegen).

## Этапность — НЕ забегать вперёд

1. **Сейчас:** schema-first. GraphQL SDL в `backend/src/schema/` — источник истины
   (контракт). Мок-сервер отдаёт фейк нужной формы на порту **4000**. Фронт
   пилится против моков. Фронтовый codegen читает схему через интроспекцию с
   `http://localhost:4000/`.
2. **Позже:** замена моков реальными резолверами в порядке важности состояния:
   **auth → матчинг → подарки/заказы → остальное**. На этом этапе появляются
   NestJS, Prisma, PostgreSQL.

**Не поднимай Prisma / Postgres / NestJS на текущем этапе.** Сейчас бэк — это
только SDL-схема + мок-сервер. База и резолверы — следующий этап.

## Два слоя типов (не путать)

Когда дойдём до резолверов, будут ДВЕ схемы про разное:

- **GraphQL SDL** (`backend/src/schema/`) — контракт API, источник истины для
  фронта и резолверов.
- **Prisma schema** (появится позже) — форма данных в БД, живёт только на бэке.

`Prisma.User` ≠ `GraphQL.User`: в БД есть `passwordHash`, в GraphQL-типе его нет.
Маппинг между ними — в резолверах. Не отдавай Prisma-объект напрямую в GraphQL.
Фронт копию схемы не хранит.

## FSD на фронте — моя редакция, соблюдать дисциплину

Feature-Sliced Design. Слои сверху вниз: `app → pages → widgets → features →
entities → shared`. Импорты строго вниз по слоям; наверх импортировать нельзя.

**Главное правило проекта:** в `entities` и `shared` кладём ТОЛЬКО то, что реально
переиспользуется в 2+ местах. Если компонент/логика используется один раз — он
живёт в своей `feature` или `page`, и НЕ выносится в общие слои ради абстрактной
«переиспользуемости». Преждевременный вынос single-use кода в shared/entities —
антипаттерн, которого избегаем осознанно (это конкретная боль, ради которой FSD
тут и применяется правильно).

Раскладка GraphQL-операций по слоям:

- Запросы данных сущности → `entities/{сущность}/api` (напр. `entities/profile/api`)
- Фрагменты (переиспользуемые наборы полей) → `entities/{сущность}/api`
- Мутации-действия → `features/{действие}/api` (напр. `features/like-user/api`)
- Инфраструктура Apollo (клиент, линк на мок-сервер) → `shared/api`
- Сгенерированные codegen типы и хуки → `shared/api/generated` (в `.gitignore`)
- shadcn-компоненты → `shared/ui`

## Доменная модель (MVP)

- **User** (аккаунт / identity) — 1:1 — **Profile** (анкета, публичное представление).
- **Profile:** `displayName`, `birthDate` (возраст ВЫЧИСЛЯЕТСЯ, не хранится),
  `gender`, `bio`; связи: `photos`, `interests` (m2m), `preference`.
- **Photo:** `url`, `type` (IMAGE/VIDEO), `position`.
- **Preference:** `genderPref`, `ageMin`, `ageMax` — кого показывать в ленте
  (отдельно от Profile: это «кого хочу видеть», а не «кто я»).
- **Like** — направленное действие (A лайкнул B), unique на пару (from, to).
- **Match** — факт взаимности; создаётся СИСТЕМОЙ при встречном лайке, не действием
  пользователя.

**Логика матчинга** (появится на этапе резолверов, кандидат на TDD): при лайке
A→B проверить, есть ли Like B→A. Если да — создать Match. Следить, чтобы не создать
дубликат матча на одну пару (соглашение по порядку id).

**MVP-скоуп:** лента (курсорная пагинация, Relay-style) + профиль + матчинг.
Чат, подарки, товары/партнёры, рестораны/бронирование — спроектированы в модели,
но реализуются позже.

**Скаляры:** `DateTime` (кастомный, через graphql-scalars), встроенный `ID`.

## Тестирование — подход

- **Фронт:** test-after (сделал компонент → покрыл поведение через RTL). НЕ TDD —
  на фронте это неестественно.
- **Бэк, доменная логика (матчинг):** пробуем TDD — правила ложатся в тесты до
  кода. Появится на этапе резолверов, не сейчас.
- Напоминание: тесты пишу я сам; ты подсказываешь, ревьюишь, оцениваешь важность
  (см. «Режим работы» и «Оценка необходимости тестов»).

## Архитектурные заметки (на потом, НЕ применять сейчас)

- Монолит. Чат — изолированный модуль внутри монолита; при росте нагрузки кандидат
  на вынос в отдельный сервис (другой характер нагрузки — постоянные WebSocket-
  соединения). Микросервисы для пет-проекта не делаем.
- Реалтайм (чат, уведомления о матчах) — через GraphQL Subscriptions, когда дойдём.
- NestJS-специфику (модули/провайдеры/DI, гарды, интерсепторы) распишем отдельно,
  когда начнётся этап резолверов и я пройду теорию по Nest.
